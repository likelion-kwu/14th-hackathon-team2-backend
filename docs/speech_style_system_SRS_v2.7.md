# 말투 설정 시스템 SRS
## Software Requirements Specification

- 문서 버전: v2.7
- 작성 기준일: 2026-08-19
- 문서 상태: MVP 구현 기준 확정본 (2026-08-19 TO_DO progression 정책까지 상위 문서와 동기화)
- 대상 기능: 카카오톡 대화 기반 사용자 말투 분석 및 미래 아바타 대사 생성
- 주요 독자: 기획자, 프론트엔드 개발자, 백엔드 개발자, AI 연동 담당자, QA 담당자, Codex CLI
- v2.7 변경 요약: 말투 분석·대사 생성 요구사항은 변경하지 않고, 상위 Avatar 정책과 비말투 데이터 유지 범위를 최종 동기화했다. 말투 초기화는 `Avatar.growthTrack`, 현재 Stage asset set, 재생성 사용 상태, 장착 Item, Point Claim/Item/Story 기록에 영향을 주지 않는다. 사용자 얼굴 사진은 말투 시스템 데이터가 아니며 Avatar 생성 요청에서만 임시 사용 후 삭제한다.
- v2.6 변경 요약: 말투 시스템 자체 요구사항은 변경하지 않고, 비말투 연계 설명을 최신 Point 정책과 동기화했다. 인증 Point는 완료 Routine에서 당일 직접 수령(PHOTO 10P/CHECK 5P, serviceDate당 최대 3개), Item은 누적 획득 Point 100P 단위로 해금하며 Point는 차감하지 않는다. 월간 경쟁은 해당 달 획득 Point 합계 공동 순위이고, 연속 하루 성공 기반 Story/Avatar Stage 정책은 유지한다.
- v2.5 변경 요약: 프론트 비동기 처리 합의에 따라 분석 Job 기본 polling 간격을 2초로 명시했다. 루틴 인증처럼 서버가 상황을 이미 알고 있는 도메인 요청은 완료 직후 대사를 가져오기 위해 별도 API를 다시 호출하지 않고 해당 응답에 선택 대사를 포함하는 연동 원칙을 추가했다. 사용자가 아바타를 직접 눌러 새 대사를 요청하는 경우에는 별도 대사 선택 API를 유지한다.
- v2.4 변경 요약: 대표 예시 수를 전 문서에서 `최대 20개`로 통일하고, 분석 작업 상태 예시를 실제 Enum과 일치시켰다. 말투 방식 전환 시 새 설정 생성·검수 성공 후 기존 설정을 원자적으로 교체하여 AI 실패로 활성 말투가 사라지지 않도록 보완했다.
- v2.3 변경 요약: 경험치 / XP 개념 제거, 누적 하루 성공 기반 아이템 해금, 연속 하루 성공 기반 스토리·아바타 외형 단계 구조에 맞춰 말투 초기화 시 유지되는 비말투 데이터 표현을 동기화
- v2.2 변경 요약: 꾸미기 재화/아이템 구매 제거 및 아이템·스토리 해금 구조에 맞춰 말투 초기화 시 유지되는 비말투 데이터 표현 동기화
- v2.1 변경 요약: 일반 게스트 세션 정책 반영, 말투 초기화 정책 확정, 프리셋 전환 시 대사 재생성 명시
- v2.0 변경 요약: 최소 루틴 관련 사전 생성 상황(`MINIMUM_ROUTINE`) 제거, 대사 상황 8개 및 총 40개로 조정

# 1. 문서 목적

본 문서는 사용자가 업로드한 카카오톡 대화 파일에서 사용자의 말투를 분석하고, 이를 바탕으로 서비스 내 "조금 더 성숙하고 건강한 미래의 나" 아바타가 사용자와 유사한 말투로 짧은 대사를 생성하는 기능의 요구사항을 정의한다.

본 문서는 다음 작업의 기준 소스로 사용한다.

- 기능 구현 범위 확정
- 프론트엔드 화면 설계
- 백엔드 API 및 데이터 모델 설계
- OpenAI API 프롬프트 설계
- 개인정보 처리 및 삭제 정책 수립
- 테스트 케이스 작성
- Codex CLI 작업 지시 및 코드 검토
- 팀원 간 기능 합의 유지

본 문서는 이 채팅에서 확정한 말투 기능만 다루며, 회원가입, 루틴 관리, 아바타 외형 생성, 피부 기록, 알림, 배포 인프라 등 다른 기능은 다루지 않는다.

### 비말투 시스템 연계 기준

말투 분석·생성 기능의 핵심 범위는 v2.3과 동일하다. v2.4에서는 문서 정합성과 방식 전환 안정성을 보완했으며, 프로젝트 전체에서 경험치 / XP 시스템은 사용하지 않는다. 말투 초기화 시 다음 비말투 상태는 삭제하지 않는다.

- 누적 하루 전체 루틴 성공 횟수
- 연속 하루 전체 루틴 성공 기록
- `TO_DO`를 제외한 완료 Routine에서 수령한 누적 Point 및 월간 Point 기록
- 누적 획득 Point 100P milestone으로 해금한 아이템
- 연속 성공일 milestone으로 영구 해금한 스토리 Episode
- 해금된 스토리에 따라 결정되는 아바타 외형 단계
- Avatar 성장 트랙과 현재 Stage 이미지 asset set
- Avatar 재생성 사용 상태

사진/체크 Point 차등은 상위 제품 문서에서 PHOTO 10P / CHECK 5P로 확정되었으며 `TO_DO`는 Point Claim 비대상이다. `TO_DO`는 인증 기록만 남고 오늘 진행률, DailySuccess, Story streak, Item/Competition Point에도 반영되지 않는다. 다만 본 말투 SRS는 해당 상세 로직을 정의하지 않고 최신 PRD/API/DB 문서를 따른다.

# 2. 시스템 목표

## 2.1 핵심 목표

사용자가 카카오톡 대화 파일을 업로드하면 시스템은 사용자 본인의 메시지를 추출하고, 말투 특징과 대표 문장 예시를 분석하여 아바타 대사 생성에 활용한다.

최종 목표는 다음 문장으로 정의한다.

> 사용자의 실제 대화에서 말투 특징과 대표 표현을 추출하고, 이를 조금 더 성숙하고 건강한 미래의 나의 말투로 재구성하여 사용자의 루틴 실행을 돕는다.

## 2.2 말투 시스템이 해야 하는 일

- 사용자의 반말/존댓말 여부를 분석한다.
- 문장 길이와 문장 리듬을 분석한다.
- 직설성, 다정함, 장난기, 감정 표현 강도를 분석한다.
- 자주 쓰는 시작 표현, 종결 표현, 반응 표현을 추출한다.
- 문장부호 사용 경향을 분석한다.
- 사용자의 실제 욕설 사용 여부와 사용 빈도를 분석한다.
- 대표 사용자 메시지를 최대 20개까지 상황 기능별로 저장한다.
- 말투 JSON과 대표 예시를 함께 사용하여 아바타 대사를 생성한다.
- 원본 카카오톡 데이터는 분석 완료 후 삭제한다.

## 2.3 말투 시스템이 하지 않는 일

- 사용자의 성격, 정신 상태 또는 건강 상태를 진단하지 않는다.
- 상대방의 말투를 사용자 말투에 포함하지 않는다.
- 카카오톡 대화 원본을 장기 저장하지 않는다.
- 사용자별 모델 파인튜닝을 하지 않는다.
- 벡터 데이터베이스를 사용하여 원문을 실시간 검색하지 않는다.
- 서비스 사용 중 자동으로 말투를 재학습하지 않는다.
- 여러 채팅방을 동시에 분석하지 않는다.
- 카카오톡 방식과 프리셋 방식을 혼합하지 않는다.

# 3. 시스템 범위

## 3.1 말투 설정 방식

사용자는 말투 설정 화면에서 다음 두 방식 중 하나를 선택한다.

1. 카카오톡 메시지 파일로 말투 생성
2. 프리셋으로 말투 생성

두 방식은 동시에 사용하지 않는다.

### 카카오톡 방식

- 사용자가 ZIP 파일을 업로드한다.
- 시스템이 대화를 분석한다.
- 말투 JSON과 대표 예시를 생성한다.
- 생성된 말투를 활성 말투로 사용한다.

### 프리셋 방식

- 사용자가 정해진 프리셋 중 하나를 선택한다.
- 카카오톡 데이터와 대표 예시는 사용하지 않는다.
- 프리셋 전용 말투 설정만 활성화한다.

### 방식 전환

방식 전환은 **새 방식의 분석·대사 생성·검수가 성공한 뒤 기존 활성 말투를 원자적으로 교체**하는 것을 원칙으로 한다.

- 카카오톡 방식에서 프리셋 방식으로 변경할 경우 선택한 프리셋 기반 사전 생성 대사 40개를 먼저 생성·검수한다. 성공한 경우에만 짧은 DB 트랜잭션에서 기존 카카오톡 기반 말투 데이터와 대사를 삭제하고 새 프리셋 프로필·대사로 교체한다.
- 프리셋 방식에서 카카오톡 방식으로 변경할 경우 새 카카오톡 분석과 사전 생성 대사 40개 생성·검수를 먼저 완료한다. 성공한 경우에만 기존 프리셋 선택값과 프리셋 기반 대사를 삭제하고 새 카카오톡 기반 프로필·대사로 교체한다.
- 새 방식의 분석 또는 대사 생성이 실패하면 현재 활성 말투를 유지하고 전환 실패를 안내한다.
- OpenAI 등 외부 API 호출을 기존 말투 삭제 트랜잭션 안에서 수행하지 않는다.
- 한 시점에 활성 말투는 하나만 존재해야 한다.
- 사용자가 명시적으로 `말투 초기화`를 선택한 경우에는 전환과 달리 현재 말투 데이터를 즉시 삭제한다.

# 4. 용어 정의

| 용어 | 정의 |
|---|---|
| 원본 ZIP | 사용자가 업로드한 카카오톡 대화 내보내기 압축 파일 |
| 파싱 데이터 | ZIP 내부 TXT에서 읽은 메시지, 참여자, 시간 등 임시 데이터 |
| 사용자 메시지 | 사용자가 참여자 목록에서 본인으로 선택한 화자의 메시지 |
| 상대방 문맥 | 사용자 메시지 직전에 작성된 상대방 메시지 1개 |
| 유효 메시지 | 시스템 메시지, 단답, 개인정보만 있는 문장 등을 제거한 분석 대상 메시지 |
| 발화 묶음 | 동일 사용자가 1분 이내에 연속으로 보낸 최대 5개 메시지를 결합한 단위 |
| 말투 프로필 | OpenAI 분석 결과로 생성된 구조화 JSON |
| 대표 예시 | 사용자 말투를 나타내기 위해 저장하는 문장 최대 20개 |
| 사전 생성 대사 | 말투 설정 완료 후 상황별로 미리 생성해 저장하는 아바타 대사 |
| 실시간 대사 | 주간 요약 등 현재 데이터가 필요한 상황에서 요청 시 생성되는 대사 |
| 프리셋 | 카카오톡 분석 없이 선택 가능한 사전 정의 말투 |
| 욕설 ON | 실제 사용자 대화에서 발견된 욕설을 일부 아바타 대사에 사용할 수 있도록 허용한 설정 |

# 5. 전체 사용자 흐름

## 5.1 카카오톡 방식 정상 흐름

```text
말투 설정 페이지 진입
-> 카카오톡 메시지 파일 선택
-> ZIP 업로드
-> 서버 파일 검증
-> TXT 추출
-> 참여자 목록 반환
-> 사용자가 본인 이름 선택
-> 사용자 메시지 및 직전 상대방 문맥 추출
-> 서버 전처리
-> 유효 메시지 수 검사
-> OpenAI 1차 분석
-> OpenAI 2차 대표 예시 선정
-> 말투 JSON 및 예시 저장
-> 상황별 아바타 대사 생성
-> 서버 검수 및 실패 대사 재생성
-> 기존 말투 덮어쓰기
-> 원본 및 임시 데이터 삭제
-> 말투 설정 완료
```

## 5.2 메시지 부족 흐름

```text
ZIP 업로드
-> 파싱 및 전처리
-> 유효 메시지 50개 미만 확인
-> "메시지 개수가 부족해 분석할 수 없습니다" 표시
-> ZIP과 파싱 데이터 즉시 삭제
-> 파일 업로드 화면 유지
-> 사용자는 다른 파일 재업로드 또는 뒤로 가서 프리셋 선택
```

## 5.3 분석 실패 흐름

```text
OpenAI 호출 실패 또는 JSON 검증 실패
-> 자동 1회 재시도
-> 재시도 성공 시 정상 처리
-> 재시도 실패 시 실패 안내
-> 임시 데이터 삭제
-> 프리셋 선택 또는 재업로드 안내
```

## 5.4 말투 방식 변경 흐름

```text
현재 카카오톡 말투 사용 중
-> 말투 설정 페이지
-> 프리셋 선택
-> 프리셋 기반 사전 생성 대사 40개 생성 및 검수
-> 성공 시 기존 카카오톡 말투 JSON, 대표 예시, 사용자 수정값, 사전 생성 대사와 원자적으로 교체
-> 실패 시 기존 카카오톡 말투 유지
```

```text
현재 프리셋 사용 중
-> 말투 설정 페이지
-> 카카오톡 파일 선택
-> 새 분석 및 카카오톡 기반 사전 생성 대사 40개 생성·검수
-> 성공 시 프리셋 선택값과 기존 프리셋 기반 대사를 새 카카오톡 말투와 원자적으로 교체
-> 실패 시 기존 프리셋 말투 유지
```

## 5.5 말투 초기화 흐름

```text
현재 카카오톡 또는 프리셋 말투 사용 중
-> 말투 설정 페이지
-> 말투 초기화 선택
-> 말투 관련 데이터 전체 삭제
-> 닉네임, Avatar 성장 트랙·Stage asset set·재생성 상태, 루틴, 인증 기록, Point 수령 기록, 누적/월간 Point, 누적 하루 성공 기록, 연속 하루 성공 기록, 획득 아이템, 스토리 해금은 유지

```

# 6. 기능 요구사항

## FR-001 말투 설정 방식 선택

시스템은 말투 설정 진입 시 다음 두 선택지를 제공해야 한다.

- 카카오톡 메시지 파일
- 프리셋

선택지는 팝업 또는 별도 페이지 형태로 구현할 수 있다.

### 완료 조건

- 사용자는 두 방식 중 하나만 선택할 수 있다.
- 현재 활성 방식이 화면에서 식별 가능해야 한다.
- 방식 변경 시 기존 방식 데이터 삭제 정책이 적용되어야 한다.

---

## FR-002 ZIP 파일 업로드

시스템은 MVP에서 채팅방 ZIP 파일 1개만 업로드할 수 있어야 한다.

### 서버 검증 항목

- 파일 확장자 또는 MIME 유형이 ZIP인지 확인
- 파일 크기 상한 확인
- 압축 해제 후 총 크기 상한 확인
- 압축 내부 경로가 안전한지 확인
- `../` 등 Zip Slip 경로 차단
- 암호화 ZIP 거부
- TXT 파일 존재 여부 확인
- 지원 가능한 카카오톡 내보내기 형식인지 확인
- 다수 TXT 파일이 존재할 경우 처리 정책에 따라 첫 지원 파일 또는 명확한 오류 반환

### 완료 조건

- 유효하지 않은 파일은 OpenAI로 전달되지 않는다.
- 서버 로그에 대화 원문을 기록하지 않는다.
- 저장 파일명은 원본명 대신 UUID를 사용할 수 있다.

---

## FR-003 참여자 목록 추출 및 본인 선택

시스템은 파싱된 카카오톡 대화에서 참여자 이름 목록을 추출해 사용자에게 보여주어야 한다.

사용자는 본인 이름을 직접 선택한다.

### 이유

- 서비스 닉네임과 카카오톡 이름이 다를 수 있다.
- 자동 추정 오류로 상대방 말투를 분석하는 문제를 방지한다.

### 완료 조건

- 사용자가 본인을 선택하기 전에는 말투 분석을 시작하지 않는다.
- 선택된 참여자의 메시지만 사용자 메시지로 처리한다.
- 참여자 이름은 OpenAI 전달 전 `[USER]`, `[PERSON]` 등으로 치환한다.

### 제외 또는 별도 처리 대상

- 사진
- 동영상
- 파일
- 이모티콘
- 송금 안내
- 입장/퇴장 안내
- 삭제 메시지
- 카카오톡 시스템 공지

## FR-006 개인정보 마스킹

OpenAI 전달 전 다음 데이터를 서버에서 마스킹해야 한다.

- 사용자 본인 이름
- 채팅방 참여자 이름
- 전화번호
- 이메일
- 계좌번호 형태
- URL

### 치환 예시

```text
이지섭 -> [USER]
성현 -> [PERSON]
010-1234-5678 -> [PHONE]
user@example.com -> [EMAIL]
https://example.com -> [URL]
```

### 범위

MVP에서는 일반 고유명사 전체를 완벽히 탐지하는 것을 목표로 하지 않는다. 확인 가능한 참여자 이름과 정규식으로 식별 가능한 민감정보를 우선 처리한다.

### 완료 조건

- 마스킹은 OpenAI 호출 이전에 완료되어야 한다.
- 원문이 서버 로그에 남아서는 안 된다.

## FR-007 긴 메시지 분리

긴 메시지는 다음 경계를 기준으로 문장 단위로 나눈다.

- 마침표 `.`
- 물음표 `?`
- 느낌표 `!`
- 줄바꿈

분리 후 지나치게 짧은 조각은 앞뒤 문장과 결합할 수 있다.

각 대표 예시의 최대 길이는 50자로 제한한다.

## FR-008 연속 메시지 결합

동일 사용자가 1분 이내에 연속으로 보낸 메시지는 하나의 발화 묶음으로 결합한다.

### 결합 제한

- 최대 5개 메시지
- 화자가 바뀌면 결합 종료
- 1분을 초과하면 새 발화 묶음 시작

### 결합 예시

```text
아니
그건 좀
아닌 거 같은데
```

결합 결과:

```text
아니 / 그건 좀 / 아닌 거 같은데
```

구분자를 유지하여 사용자의 메시지 분할 리듬을 분석할 수 있게 한다.

## FR-009 단답 메시지 제외

단답 메시지는 최종 분석 표본과 대표 예시에서 제외한다.

예시:

- ㅇㅇ
- ㄴㄴ
- 왜
- 응
- 아
- ㅋㅋ

단, 반복 표현 빈도는 전처리 통계로 따로 계산해 말투 JSON 생성 시 참고 정보로 제공할 수 있다.

### 확정 원칙

- 단답 자체는 대표 예시로 저장하지 않는다.
- 중복 빈도는 말버릇 통계에 반영할 수 있다.

---

## FR-010 중복 메시지 처리

동일하거나 정규화 후 동일한 문장은 대표 예시 후보에는 한 번만 남긴다.

그러나 반복 빈도는 별도 통계로 보존하여 자주 쓰는 표현 분석에 사용할 수 있다.

### 예시

```text
ㅇㅇ x 18회
알겠어 x 7회
```

대표 예시에는 각 1개 이하만 남기며, 빈도 정보는 별도 전달한다.

---

## FR-011 상대방 문맥 사용

사용자 메시지의 의미를 이해하기 위해 직전 상대방 메시지 1개를 문맥으로 사용할 수 있다.

### 규칙

- 시간 차이와 관계없이 바로 직전 상대방 메시지 1개를 연결한다.
- 연속된 상대방 메시지 여러 개는 MVP에서 합치지 않는다.
- 상대방 메시지는 말투 분석 대상이 아니다.
- 상대방 표현을 말투 특징이나 대표 예시에 포함하면 안 된다.
- 분석 완료 후 상대방 문맥은 저장하지 않는다.

### OpenAI 전달 구조 예시

```json
{
  "context": "[PERSON] 오늘 운동했어?",
  "userMessage": "아니 오늘은 했거든"
}
```

### 프롬프트 필수 규칙

- `context`는 의미 해석 전용이다.
- 말투 특징은 반드시 `userMessage`만 기준으로 추출한다.
- `context`의 어휘나 표현은 사용자 말투로 학습하지 않는다.

---

## FR-012 유효 메시지 최소 개수

말투 분석은 전처리 완료 후 유효 사용자 메시지가 50개 이상일 때만 수행한다.

### 50개 미만 처리

- 분석 API를 호출하지 않는다.
- 오류 메시지를 표시한다.
- 원본 ZIP과 파싱 데이터를 즉시 삭제한다.
- 업로드 화면은 유지한다.
- 사용자는 다른 파일을 올리거나 뒤로 가서 프리셋을 선택할 수 있다.

---

## FR-013 분석 입력 최대 개수

OpenAI 분석에는 최신 유효 메시지부터 최대 500개만 사용한다.

### 정렬 및 절단 규칙

1. 메시지를 최신 순으로 정렬
2. 최신 메시지부터 최대 500개 선택
3. 500개를 초과한 오래된 메시지는 분석에서 제외

최근 말투에 더 큰 비중을 두며, 별도의 기간 선택이나 균형 샘플링은 하지 않는다.

## FR-014 OpenAI 1차 분석

OpenAI 1차 호출은 다음 작업을 수행한다.

- 말투 JSON 생성
- 메시지 기능 분류
- 대표 예시 후보 선정

### 입력

- 전처리된 사용자 메시지 최대 500개
- 필요한 메시지의 직전 상대방 문맥 1개
- 반복 표현 빈도 통계
- 사용자 선택값이 있는 경우 해당 값
- 출력 JSON 스키마

### 출력

- 말투 프로필 JSON
- 각 후보 메시지의 기능 분류
- 카테고리별 대표 후보 목록
- 실제 대화에서 발견된 욕설 목록 및 빈도

### 카테고리

- `QUESTION`
- `AGREEMENT`
- `DISAGREEMENT`
- `ENCOURAGEMENT`
- `REACTION`
- `GENERAL`

`JOKE` 카테고리는 별도로 두지 않으며 장난기는 말투 JSON 속성으로 관리한다.

## FR-015 OpenAI 2차 분석

OpenAI 2차 호출은 다음 작업을 수행한다.

- 최종 대표 예시 최대 20개 선정
- 특정 카테고리에 적합한 실제 메시지가 없으면 말투 기반 합성 예시 생성

### 입력

- 1차 말투 JSON
- 카테고리별 대표 후보
- 후보 출처 정보
- 최대 예시 수와 길이 조건

### 출력

- 최종 대표 예시 최대 20개
- 각 예시의 카테고리
- 각 예시의 출처
- 필요 시 AI 생성 보완 예시

### 출처 구분

- `USER_MESSAGE`: 실제 사용자 메시지 기반
- `AI_GENERATED`: 부족한 카테고리를 보완하기 위해 생성된 문장

### 비용 최적화

2차 호출에는 원본 메시지 전체를 다시 보내지 않는다. 1차에서 압축된 말투 JSON과 대표 후보만 전달한다.

운영 비용 또는 지연이 예상보다 큰 경우 1차와 2차를 단일 호출로 통합할 수 있으나, MVP 기본안은 2회 호출이다.

# 7. 말투 프로필 요구사항

```json

  "directness": "HIGH",
  "warmth": "MEDIUM",
  "playfulness": "LOW",
  "emotionalIntensity": "MEDIUM",
  "openingPatterns": ["아니", "근데"],
  "endingPatterns": ["~지", "~같은데", "~하면 됨"],

    "questionMark": "MEDIUM",

    "enabledByUser": false,

```

- `BANMAL`
- `JONDAEMAL`

### sentenceLength

- `SHORT`
- `MEDIUM`
- `LONG`

- `LOW`
- `MEDIUM`
- `HIGH`

### 욕설 빈도

- `NONE`
- `LOW`
- `MEDIUM`
- `HIGH`

# 9. 욕설 처리 요구사항

## 9.1 기본 정책

욕설 설정 기본값은 OFF이다.

실제 사용자 대화에서 욕설이 탐지된 경우에만 사용자가 ON으로 변경할 수 있다.

욕설이 탐지되지 않은 경우 욕설 ON 설정은 비활성화한다.

## 9.2 허용 범위

욕설 ON 시 다음 조건을 모두 만족할 때만 욕설을 사용할 수 있다.

- 사용자의 실제 대화에서 발견된 욕설일 것
- 실제 사용 빈도를 반영할 것
- 사용자 자신을 독려하는 문맥일 것
- 아바타 대사의 핵심 목적이 행동 유도 또는 격려일 것
- 인신공격이 아닐 것

## 9.3 금지 범위

욕설 ON이어도 다음은 항상 금지한다.

- 인신공격
- 존재나 능력 비하
- 혐오 표현
- 외모 비하
- 자해 또는 죽음 유도
- 협박
- 질병이나 건강 문제를 이용한 압박
- 행동 제안 없이 모욕만 하는 문장

### 허용 가능 예

```text
지섭아 씨발 정신 차리자. 세안 하나는 하고 자.
```

### 금지 예

```text
그것도 못 하면 넌 진짜 병신이다.
```

## 9.4 적용 범위

욕설 ON은 사전 생성 대사와 실시간 생성 대사 모두에 적용 가능하다.

다만 상황별 생성 규칙과 실제 욕설 빈도에 따라 사용 비율을 제한한다.

## 9.5 내부 고정값

```json
{
  "personalInsultAllowed": false
}
```

이 값은 사용자가 변경할 수 없고 항상 false이다.

# 11. 아바타 대사 생성 요구사항

## 11.1 아바타 역할

아바타는 현재 사용자의 복제본이 아니라 "조금 더 성숙하고 건강한 미래의 나"이다.

개념적으로 다음 비율을 사용한다.

- 현재 사용자 말투 특성: 80%
- 미래의 나다운 안정감과 건강한 행동 유도: 20%

이 비율은 정확한 수치 계산용 필드가 아니라 프롬프트 설계 원칙이다.

## 11.2 대사 생성 입력

- 현재 사용자 상황
- 전달 목적
- 말투 JSON
- 현재 상황과 관련 있는 대표 예시
- 욕설 허용 설정
- 사용자 표시 이름
- 최대 길이
- 안전 규칙

## 11.3 대사 최대 길이

모든 짧은 아바타 말풍선 대사는 공백을 포함하여 최대 50자로 제한한다.

주간 요약 등 긴 요약 기능은 이 SRS의 대상이 아니며 별도 기능으로 분리한다.

## 11.4 이름 사용

사용자 이름은 가끔 사용한다.

상황별 사전 생성 대사 5개 중 최대 1개만 사용자 이름을 포함할 수 있다.

이름은 말투 분석 데이터에 포함하지 않고 대사 생성 시 별도 변수로 전달한다.

## 11.5 사전 생성 상황

다음 8개 상황에 대해 각각 5개 대사를 생성한다.

| 코드 | 의미 |
|---|---|
| ROUTINE_UPCOMING | 루틴 시작 전 |
| ROUTINE_AVAILABLE | 루틴 수행 가능 시간 진입 |
| ROUTINE_REMINDER | 정해진 시간 내 미완료 |
| ROUTINE_COMPLETED | 개별 루틴 완료 |
| ALL_COMPLETED | 오늘의 진행률 대상 루틴 모두 완료 (`TO_DO` 제외) |
| STREAK_CONTINUED | 연속 실천 기록 유지 |
| STREAK_BROKEN | 연속 기록 중단 |
| RETURN_AFTER_ABSENCE | 며칠 만에 다시 복귀 |

총 기본 생성 수는 사용자당 40개이다.

## 11.6 대사 선택

대사는 다음 규칙으로 선택한다.

1. 해당 상황의 활성 대사 목록 조회
2. 최근 사용한 대사 제외
3. 남은 대사 중 무작위 선택
4. 모두 최근 사용된 경우 가장 오래 사용하지 않은 대사부터 다시 후보에 포함

## 11.7 프론트 전달 방식

프론트가 하나의 사용자 행동을 처리하기 위해 도메인 API 호출 직후 다시 대사 API를 호출하는 구조는 피한다.

백엔드가 요청 처리 과정에서 상황을 이미 명확히 판정할 수 있는 경우 선택된 대사를 **기존 도메인 응답에 함께 포함**한다.

기본 예:

```text
개별 루틴 인증 성공 + 오늘 일부 미완료
→ ROUTINE_COMPLETED

마지막 진행률 대상 루틴 인증 성공 + 오늘 진행률 대상 전체 완료 (`TO_DO` 제외)
→ ALL_COMPLETED
```

이 경우 프론트는 인증 성공 직후 `avatar-dialogues` API를 추가 호출하지 않는다.

반대로 사용자가 홈에서 아바타를 직접 눌러 새로운 대사를 요청하는 것처럼 독립적인 상호작용은 별도 대사 선택 API를 사용할 수 있다.

이 원칙은 `AvatarDialogue` 저장 구조나 8개 상황 × 5개 생성 정책을 변경하지 않는다.

# 12. 생성 결과 검수

OpenAI가 생성한 대사는 바로 저장하지 않고 서버 규칙 검사를 통과해야 한다.

## 12.1 검사 항목

- 최대 50자 여부
- 빈 문자열 여부
- 욕설 OFF인데 욕설 포함 여부
- 허용 목록에 없는 욕설 포함 여부
- 인신공격 금지 표현 포함 여부
- 혐오, 협박, 자해 유도 표현 포함 여부
- 이름 사용 빈도 초과 여부
- 상황에 맞지 않는 대사 여부
- 동일 문장 중복 여부
- 실제 사용자 예시를 과도하게 그대로 복사했는지 여부

## 12.2 실패 처리

검수 실패 문장만 재생성한다.

전체 40개를 다시 생성하지 않는다.

재생성에도 실패하면 해당 상황에 안전한 기본 대사를 사용하거나 생성 실패 상태를 기록한다.

전체 프로젝트 API 명세에서는 Job 조회 Endpoint를 제공해야 한다.

```http

```

```json
{
  "jobId": "uuid",

  "result": {
    "sourceType": "KAKAO_CHAT",
    "dialogueCount": 40,
    "validMessageCount": 237

```

`COMPLETED`, `FAILED`, `EXPIRED`에서는 polling을 종료한다.

## 15.6 말투 초기화

```http
DELETE /api/v1/speech-style
```

이 API는 사용자에게 `말투 초기화` 기능으로 제공한다.

초기화 시 현재 말투 방식이 카카오톡 기반인지 프리셋 기반인지와 관계없이 다음 데이터를 모두 삭제한다.

- 활성 말투 방식 및 프리셋 선택값
- 말투 프로필 JSON
- 사용자 수정값
- 대표 예시와 카테고리·출처
- 사전 생성 대사 40개 및 사용 이력
- 욕설 탐지·사용 설정
- 분석에 사용된 유효 메시지 개수 등 말투 분석 메타데이터

다음 데이터는 삭제하지 않는다.

- 닉네임
- 아바타와 성장 상태
- 루틴
- 누적 하루 전체 루틴 성공 횟수
- 연속 하루 전체 루틴 성공 기록
- Point 수령 기록 및 누적/월간 획득 Point
- 획득 아이템 및 Point milestone 아이템 해금 기록
- 스토리 Episode 해금 기록
- 아이템 및 인벤토리
- 루틴 인증·수행 기록

초기화 성공 후 활성 말투가 없는 상태가 되며, 클라이언트는 말투 설정 화면으로 이동해야 한다. 사용자가 카카오톡 또는 프리셋 중 하나를 다시 설정하기 전까지 홈 진입을 허용하지 않는다.

## 15.7 프리셋 선택

```http
POST /api/v1/speech-style/preset
```

프리셋 선택 시 프리셋 기반 사전 생성 대사 40개를 먼저 생성·검수한다. 성공한 경우에만 기존 카카오톡 말투 데이터를 삭제하고 새 프리셋 프로필·대사로 원자적으로 교체한다. 생성 또는 검수에 실패하면 기존 활성 말투를 유지한다.

# 16. 상태 요구사항

## 16.1 분석 작업 상태

- `UPLOADED`
- `WAITING_PARTICIPANT_SELECTION`
- `PREPROCESSING`
- `ANALYZING`
- `GENERATING_DIALOGUES`
- `COMPLETED`
- `FAILED`
- `EXPIRED`

## 16.2 10분 만료 정책

분석 임시 데이터의 최대 보관 시간은 10분이다.

10분이 지나면:

- 작업 상태를 `EXPIRED` 또는 `FAILED`로 변경
- ZIP과 파싱 데이터 삭제
- 늦게 도착한 OpenAI 응답은 폐기
- 늦은 응답이 현재 사용자 설정을 덮어쓰지 못하도록 작업 ID와 상태를 재검증

분석 화면은 단계별 진행률 대신 단순 로딩만 표시한다.

```text
말투를 분석하는 중입니다...
```

## 16.3 Job 상태 polling

본인 참여자를 선택해 분석을 시작한 뒤 프론트는 Job 상태 조회 API를 기본 **2초 간격**으로 호출한다.

```text
POST analyze
→ 202 Accepted
→ 2초 후 첫 상태 조회
→ 처리 중이면 2초 간격 반복
→ COMPLETED / FAILED / EXPIRED에서 즉시 종료
```

- 1초 이하의 과도한 polling을 기본값으로 사용하지 않는다.
- 브라우저 백그라운드 전환 등으로 polling 간격이 늘어나는 것은 허용한다.
- Job 만료 정책은 기존 10분을 유지한다.
- 서버가 추후 `pollAfterMs`를 응답하면 클라이언트는 그 값을 우선할 수 있다.

# 18. 보안 및 개인정보 요구사항

## 18.1 최소 수집

사진, 파일, 연락처, 계좌정보 등은 분석 대상이 아니다.

## 18.2 원본 삭제

### 분석 성공

다음 데이터를 즉시 삭제한다.

- 원본 ZIP
- 추출 TXT
- 전체 파싱 데이터
- 상대방 문맥
- 임시 분석 파일

### 유효 메시지 부족

위 데이터를 즉시 삭제한다.

### 분석 실패 또는 만료

재시도 또는 10분 보관 정책이 끝나면 모두 삭제한다.

## 18.3 로그 정책

로그에 다음 정보를 남기지 않는다.

- 카카오톡 대화 원문
- 대표 예시 원문
- 상대방 메시지
- 개인정보가 포함된 OpenAI 요청/응답 전문

로그에는 작업 ID, 사용자 ID, 상태, 오류 코드, 처리 시간, 메시지 개수 등의 메타데이터만 남긴다.

## 18.4 API 키

OpenAI API 키는 서버 환경 변수로만 관리한다.

프론트엔드 코드, Git 저장소, 로그에 노출하지 않는다.

## 18.5 전송 보안

- 운영 환경에서 HTTPS 사용
- 업로드 크기 제한
- 유효한 일반 게스트 세션 또는 인증 사용자만 말투 파일 업로드 가능
- 게스트 식별자 또는 인증 사용자 ID 기준으로 사용자별 작업 접근 권한 확인
- 다른 사용자의 분석 작업 ID 접근 차단

# 19. 비기능 요구사항

## NFR-001 성능

- ZIP 파싱과 전처리는 일반적인 파일에서 수 초 이내 완료되는 것을 목표로 한다.
- OpenAI 응답 시간을 제외한 서버 전처리는 동기 처리 가능해야 한다.
- 분석 입력은 최대 500개 메시지로 제한한다.
- 2차 호출에는 전체 원문을 다시 전송하지 않는다.

## NFR-002 비용

- 전체 카카오톡 원문을 매번 대사 생성 시 보내지 않는다.
- 전체 원문은 최초 분석에만 사용한다.
- 이후 대사 생성에는 말투 JSON과 관련 대표 예시만 사용한다.
- 자주 발생하는 8개 상황의 대사는 미리 생성한다.
- 실패한 대사만 재생성한다.

## NFR-003 안정성

- OpenAI 호출 실패 시 자동 1회 재시도한다.
- JSON 응답은 서버 스키마 검증을 통과해야 한다.
- 늦은 응답이 최신 설정을 덮어쓰지 않도록 작업 상태를 확인한다.
- 안전한 기본 대사 또는 프리셋으로 복구 가능한 구조를 갖는다.

## NFR-004 유지보수성

- 카카오톡 파서, 전처리기, AI 분석기, 대사 생성기, 검수기를 분리한다.
- 시스템 메시지 패턴과 금칙어는 설정 파일 또는 상수 모듈로 관리한다.
- OpenAI 모델명과 프롬프트 버전은 코드에 흩어놓지 않고 중앙 관리한다.
- 프롬프트 버전을 DB 또는 로그 메타데이터에 기록할 수 있다.

## NFR-005 개인정보

- 원본은 분석 완료 후 즉시 삭제한다.
- 장기 저장 데이터는 말투 JSON, 대표 예시, 사전 대사로 제한한다.
- 사용자가 말투 초기화 시 말투 관련 데이터만 모두 삭제하고, 닉네임·Avatar 성장 트랙/Stage asset/재생성 상태·루틴·인증·Point 수령·누적/월간 Point·누적/연속 하루 성공 기록·아이템·스토리 해금 데이터는 유지한다.

# 21. OpenAI 1차 프롬프트 요구사항

다음은 실제 프롬프트 전문이 아니라 필수 지침 구조이다.

## System 역할

```text
너는 한국어 대화의 문체와 표현 습관을 분석하는 시스템이다.
사용자의 성격, 건강 상태, 정신 상태를 진단하지 않는다.
context는 userMessage의 의미를 이해하기 위한 참고자료일 뿐이다.
말투 특징은 반드시 userMessage만을 기준으로 분석한다.
반드시 지정된 JSON 스키마로만 응답한다.
```

## 입력 단위

```json
{
  "id": "m-001",
  "context": "[PERSON] 오늘 운동했어?",
  "userMessage": "아니 오늘은 했거든"
}
```

## 분석 지침

- 사용자 메시지의 기능을 6개 카테고리 중 하나로 분류
- 대표성 높은 후보 식별
- 상대방 표현을 사용자 스타일에 포함하지 않음
- 개인정보 추론 금지
- 사용자가 실제 사용한 욕설만 추출
- 욕설의 빈도와 사용 맥락 요약
- 긴 설명보다 구조화 속성 우선
- 수치 정확도나 신뢰도를 임의 생성하지 않음

# 25. 인수 조건

다음 조건을 모두 만족하면 말투 설정 기능의 MVP 구현이 완료된 것으로 판단한다.

1. 사용자가 카카오톡 ZIP 1개를 업로드할 수 있다.
2. 서버가 ZIP을 안전하게 검증하고 TXT를 파싱한다.
3. 참여자 목록에서 사용자가 본인을 선택할 수 있다.
4. 시스템 메시지와 단답 메시지를 제거한다.
5. 개인정보를 OpenAI 전달 전에 마스킹한다.
6. 같은 사용자의 1분 이내 연속 메시지를 최대 5개 결합한다.
7. 최신 유효 메시지 최대 500개만 사용한다.
8. 유효 메시지 50개 미만일 경우 API를 호출하지 않고 파일을 삭제한다.
9. 직전 상대방 메시지 1개를 문맥으로 활용하되 저장하지 않는다.
10. OpenAI 1차와 2차 호출을 통해 말투 JSON과 대표 예시를 생성한다.
11. 대표 예시는 최대 20개이며 출처를 구분한다.
12. 사용자가 말투 세부 옵션을 수정할 수 있다.
13. 욕설은 실제 사용 이력이 있을 때만 ON 가능하다.
14. 모든 아바타 짧은 대사는 최대 50자이다.
15. 8개 상황마다 5개 대사를 생성한다.
16. 대사는 서버 정책 검사를 통과한 경우에만 저장한다.
17. 최근 사용 대사를 제외하고 무작위 선택한다.
18. 분석 성공, 실패, 메시지 부족, 만료 시 원본 데이터가 정책대로 삭제된다.
19. 말투 설정 변경 시 기존 대사가 전부 재생성된다.
20. 카카오톡과 프리셋은 동시에 활성화되지 않는다.
21. 말투 초기화 시 말투 관련 데이터가 모두 삭제되고 비말투 사용자 데이터는 유지되며, 재설정 전에는 홈 진입이 차단된다.
22. API 키와 대화 원문이 Git 또는 로그에 포함되지 않는다.

# 부록 B. 최종 설계 원칙

이 기능은 "사용자의 모든 카카오톡 대화를 기억하는 AI"를 만드는 기능이 아니다.

원본 대화는 최초 말투 분석을 위한 일회성 입력이다. 분석이 끝난 뒤에는 다음 데이터만 남긴다.

```text
말투 프로필 JSON
+ 대표 예시 최대 20개
+ 상황별 사전 생성 대사
```

아바타는 사용자 말투를 그대로 복제하지 않는다. 사용자의 문장 리듬과 표현 습관을 유지하면서도, 루틴 실행을 돕는 조금 더 성숙하고 건강한 미래의 나로 재구성한다.

이 원칙은 구현 편의보다 우선하며, 개인정보 최소 수집, 원본 삭제, 사용자 선택권, 인신공격 금지 규칙을 항상 지켜야 한다.
