# 갓생사자 백엔드 구현 업무 분배 지침

> 기준 시점: 2026-08-19
> 목적: DB 19개 테이블 skeleton 및 API 35개 endpoint skeleton 이후, 실제 Business Logic 구현을 3개 파트로 나누어 진행하기 위한 팀 공통 지침

---

## 1. 현재 상태

현재 백엔드에는 다음 기반 작업이 완료되어 있다.

- 공통 API / Error / Auth / Time foundation
- Flyway V1~V4 migration
- DB 19개 테이블 skeleton
- Entity / Repository skeleton
- API Specification v4.3 기준 35개 endpoint skeleton
- 미구현 Business Logic은 `FeatureNotImplementedException` 기반 HTTP 501 처리
- `gradlew test`, `gradlew build` 통과

이제부터는 새로운 구조를 크게 추가하기보다 **기존 Controller / DTO / Service / Entity / Repository 구조를 따라 실제 기능을 완성하는 것**을 우선한다.

---

## 2. 공통 개발 원칙

### 2.1 구현 전

작업을 시작하기 전에 반드시 다음 파일과 현재 코드를 확인한다.

- `AGENTS.md`
- `docs/갓생사자_API_SPEC_v4.3.md`
- `docs/갓생사자_backend_database_design_v1.8.md`
- `docs/갓생사자_PRD_v2.1.md`
- Speech 관련 작업은 `docs/speech_style_system_SRS_v2.7.md` 추가 확인

Codex CLI 사용 시 한 번에 큰 범위를 구현하지 않고 다음 순서를 따른다.

1. 관련 코드 검색 및 현재 구조 분석
2. 구현 계획 출력
3. 수정/생성 파일 목록 확인
4. 구현
5. 테스트
6. 빌드
7. 변경 파일 및 남은 TODO 정리

### 2.2 공통 금지 사항

- 기존 V1~V4 migration을 임의 수정하지 않는다.
- Entity field를 문서 확인 없이 추가하지 않는다.
- `DailyRoutine.status` 같은 중복 상태 컬럼을 추가하지 않는다.
- Point wallet / balance / XP / Coin 개념을 추가하지 않는다.
- client가 전달한 `userId`, `ownerId`, `guestId`를 권한 판정에 사용하지 않는다.
- 비밀키, DB 비밀번호, OpenAI API Key를 저장소에 커밋하지 않는다.
- 실제 사용자 사진, Kakao 원문 등 민감 데이터를 장기 저장하지 않는다.
- 다른 파트가 소유한 핵심 Service 파일을 사전 상의 없이 수정하지 않는다.

### 2.3 공통 검증

작업 단위가 끝날 때마다 최소한 다음을 실행한다.

```powershell
.\gradlew.bat test
.\gradlew.bat build
```

둘 중 하나라도 실패하면 원인을 해결한 뒤 공유한다.

# 3. 파트 A — Core / Auth / Progression

## 3.1 담당 목적

모든 도메인이 사용할 수 있는 **공통 실행 기반과 인증 흐름**을 연결하고, 루틴 완료 이후의 핵심 성장/보상 흐름을 책임진다.

## 3.2 소유 범위

주요 소유 패키지:

```text
session/**
common/auth/**
routine/daily/**
routine/verification/**   ← PHOTO AI 판정 모듈 자체는 Part B
routine/point/**
record/**
competition/**
home/**
```

추가로 다음 도메인의 **해금/상태 변경 로직**을 담당한다.

- DailySuccess
- Item Unlock
- Story Unlock / Streak

## 3.3 우선 구현 순서

### A-1. DB 연결 및 공통 실행 기반

다음 환경변수를 사용하는 Spring datasource 설정을 연결한다.

```text
DB_URL
DB_USERNAME
DB_PASSWORD
```

목표:

- PostgreSQL 실제 접속
- Flyway V1~V4 정상 적용 확인
- JPA Repository 실제 사용 가능 상태 확인

주의:

- DB 비밀번호를 `application.yaml`에 직접 작성하지 않는다.
- 새로운 DB 구조가 필요하면 기존 migration을 수정하지 말고 별도 migration 추가 여부를 팀과 먼저 논의한다.

### A-2. Guest Session / 인증

구현 흐름:

```text
POST /api/v1/sessions
→ User 생성/조회
→ GuestSession 생성
→ opaque token 발급
→ token hash 저장

Authorization: Bearer <token>
→ token hash 조회
→ GuestSession
→ User
→ CurrentUserProvider
```

완료 조건:

- 이후 모든 도메인이 client `userId` 없이 현재 사용자를 식별할 수 있어야 한다.
- 인증되지 않은 요청은 공통 Error 규칙으로 처리한다.

### A-3. DailyRoutine

담당:

- 날짜 기준 DailyRoutine materialization
- Routine repeat rule 반영
- serviceDate 기준 조회
- API 상태 파생

상태:

```text
UPCOMING
AVAILABLE
COMPLETED
FAILED
```

주의:

- 상태를 DB 컬럼으로 저장하지 않는다.
- 현재 시각, Verification 존재 여부 등 Source of Truth에서 계산한다.

### A-4. CHECK 인증

우선 CHECK 인증을 먼저 완성하여 AI 없이 핵심 루프를 검증한다.

```text
DailyRoutine 조회
→ 소유권 확인
→ 인증 가능 시간 확인
→ 중복 인증 확인
→ RoutineVerification(CHECK)
→ DailySuccess 재평가
→ 응답
```

### A-5. PHOTO 인증 orchestration

PHOTO의 OpenAI 이미지 판정 구현은 Part B가 담당한다.

Part A는 전체 인증 Service 흐름을 담당한다.

```text
RoutineVerificationService
→ Part B의 PhotoVerificationAnalyzer 호출
→ 판정 결과 확인
→ RoutineVerification(PHOTO) 저장
→ DailySuccess 재평가
→ 응답
```

Part A와 B가 같은 PHOTO Service를 동시에 수정하지 않도록 경계를 유지한다.

### A-6. Point Claim

정책:

```text
PHOTO 인증 완료 → Claim 시 10P
CHECK 인증 완료 → Claim 시 5P
serviceDate 기준 최대 3개 Claim
```

중요:

- 인증 성공 시 Point를 자동 지급하지 않는다.
- 사용자가 별도 Point Claim API를 호출해야 한다.
- 클라이언트에게 Point 금액을 입력받지 않는다.
- Source of Truth는 `RoutinePointClaim`이다.
- 동시 요청으로 중복 지급되지 않도록 처리한다.

### A-7. DailySuccess / Story / Item Unlock

#### DailySuccess

TO_DO를 제외한 해당 날짜의 대상 Routine을 기준으로 판정한다.

#### Story

연속 DailySuccess:

```text
7일 → EP.1
14일 → EP.2
21일 → EP.3
28일 → EP.4
35일 → EP.5
```

Avatar Stage:

```text
Story 없음 → Stage 1
EP.1 → Stage 2
EP.2 이상 → Stage 3
```

Stage는 Avatar DB에 중복 저장하지 않고 Story 상태에서 파생한다.

#### Item Unlock

누적 Claim Point 기준:

```text
100P 단위 도달
→ 아직 보유하지 않은 활성 Item 중 1개 랜덤 해금
```

Point는 차감하지 않는다.

### A-8. Record / Competition / Home

마지막 통합 단계에서 구현한다.

#### Record

기존 DB Source of Truth를 집계한다.

#### Competition

- Asia/Seoul 기준 월별 실제 Claim Point 합계
- `RoutinePointClaim.amount` SUM
- 동점 순위: `1, 2, 2, 4`

별도 leaderboard 테이블을 만들지 않는다.

#### Home

다른 파트 기능이 충분히 완료된 뒤 마지막으로 통합한다.

# 4. 파트 B — AI / Avatar / Speech

## 4.1 담당 목적

OpenAI 및 파일 처리가 필요한 기능을 전담한다.

## 4.2 소유 범위

```text
avatar/**
speech/**
```

PHOTO 인증에서는 아래와 같이 **AI 판정 모듈만 명확히 분리하여 소유**한다.

예시:

```text
routine/verification/photo/**
```

권장 책임:

```text
PhotoVerificationAnalyzer
PhotoVerificationAnalysis
OpenAiPhotoVerificationAnalyzer
```

기존 전체 `RoutineVerificationService` orchestration은 Part A가 소유한다.

## 4.3 우선 구현 순서

```text
1. PHOTO AI 판정
2. Avatar DEFAULT / 파일 조회
3. Avatar AI 생성
4. Speech Preset / Dialogue
5. Kakao ZIP parsing
6. Speech OpenAI 분석
```

PHOTO 인증은 핵심 기능이므로 우선순위를 높게 둔다.

## 4.4 PHOTO AI 인증

담당:

- multipart 사진 입력 처리
- 인증 물건 판정
- 요청된 손동작/미션 판정
- OpenAI Vision 요청
- 구조화된 판정 결과 반환
- API 실패 / timeout / 판정 불가 처리
- 임시 사진 삭제

주의:

- 원본 인증 사진을 DB에 영속 저장하지 않는다.
- 원본 사진 내용을 로그로 출력하지 않는다.
- OpenAI 호출은 DB transaction 밖에서 수행한다.

Part A에게 반환할 결과는 가능한 한 단순한 구조로 유지한다.

예:

```text
passed
objectMatched
gestureMatched
reasonCode
```

실제 필드는 현재 API/Service 구조를 확인하여 결정한다.

## 4.5 Avatar

담당:

- Avatar 생성
- DEFAULT fallback
- Stage1 / Stage2 / Stage3 이미지
- Avatar 이미지 조회
- 전체 세트 재생성
- Item 장착 API
- 저장 파일 관리

정책:

- 성장 트랙: `SKIN`, `WELL_BEING`, `HEALTH_FIT`, `DIET`
- TO_DO는 Avatar 성장 트랙이 아니다.
- 얼굴 사진은 optional
- 얼굴 사진은 피부/건강 상태 분석에 사용하지 않는다.
- 얼굴 참조 용도로만 사용한다.
- 원본 face photo는 영구 저장하지 않는다.
- 생성 이미지 규격: `250 × 500 PNG RGBA transparent`
- Stage1 생성 후 Stage2/3은 Stage1 기반으로 독립 생성
- 최초 생성 실패 시 1회 재시도 후 DEFAULT 세트 사용
- onboarding 중 전체 세트 재생성 성공은 최대 1회
- 미래 Stage 이미지는 사용자에게 미리 노출하지 않는다.

## 4.6 Speech Preset / Dialogue

먼저 OpenAI 없이 Preset 흐름을 완성한다.

담당:

- Speech preset 적용
- SpeechStyleProfile 저장/교체
- Avatar Dialogue 조회/선택
- 8개 situation × 5개 = 40개 Dialogue 관리

Avatar Dialogue 최대 길이는 50자 정책을 유지한다.

## 4.7 Kakao / Speech AI

흐름:

```text
ZIP 업로드
→ 임시 저장
→ 참여자 분석
→ participant 선택
→ preprocessing
→ 개인정보 masking
→ OpenAI 말투 분석
→ Example / Dialogue 생성
→ Profile atomic replace
→ 원본 임시 데이터 삭제
```

원칙:

- ZIP/TXT 원문 장기 저장 금지
- 상대방 대화 맥락 장기 저장 금지
- OpenAI prompt/response 장기 저장 금지
- 분석 완료/실패 후 임시 파일 정리
- 외부 API 실패 처리 필수

## 5.2 소유 범위

```text
user/**

단, 아래 제외:
```

```text
GET    /api/v1/routines

PATCH  /api/v1/routines/{routineId}
```

카테고리:

```text
SKIN
WELL_BEING
HEALTH_FIT
DIET
```

```text
DAILY
DAYS_OF_WEEK
```

주요 검증:

Routine 수정이 과거/현재 DailyRoutine에 미치는 영향은 문서 정책을 확인하고 구현한다.

## 5.5 Routine Recommendation


- 최대 약 3개

## 5.7 Photo Mission

```text

```

담당:

# 6. TO_DO 공통 정책 — 확정

`TO_DO`는 일반 웰니스 Routine과 별도의 보조 일회성 할 일이다.

```text
TO_DO
├─ DailyRoutine 생성 가능
├─ 완료/인증 가능
├─ 오늘 진행률 제외
├─ DailySuccess 판정 제외
├─ Story Streak 제외
├─ Point Claim 불가
├─ Item Unlock 영향 없음
└─ Competition 점수 영향 없음
```

즉:

```text
오늘 진행률
= TO_DO가 아닌 DailyRoutine만 계산

DailySuccess
= TO_DO가 아닌 대상 Routine이 모두 성공했는지 계산
```

TO_DO 인증이 성공한 경우 `RoutineVerification`을 통한 완료 표시는 가능하지만, Point/성장/경쟁 시스템에는 연결하지 않는다.

# 7. PHOTO / CHECK 인증 공통 정책

일반 Routine은 두 방식 모두 지원한다.

### CHECK

```text
CHECK 성공
→ RoutineVerification(CHECK)
→ 완료
→ DailySuccess 재평가
→ 사용자 Point Claim
→ 5P
```

### PHOTO

```text
PHOTO 성공
→ RoutineVerification(PHOTO)
→ 완료
→ DailySuccess 재평가
→ 사용자 Point Claim
→ 10P
```

중요:

- 인증 성공과 Point 지급은 분리한다.
- Point는 사용자가 완료 Routine을 눌러 별도로 Claim한다.
- serviceDate 기준 최대 3개까지 Claim할 수 있다.
- TO_DO는 Claim 대상이 아니다.

# 12. 완료 조건

각 파트의 기능은 단순히 컴파일되는 것이 아니라 다음을 만족해야 완료로 본다.

- API Specification의 Request/Response 계약을 지킨다.
- 실제 DB에서 정상 동작한다.
- 본인 리소스 소유권을 검증한다.
- 잘못된 입력을 처리한다.
- 외부 API 실패를 처리한다.
- 중복 요청을 고려한다.
- 민감정보를 저장/로그에 남기지 않는다.
- `gradlew test` 통과
- `gradlew build` 통과
- 다른 파트의 기존 기능을 깨뜨리지 않는다.

## 최종 목표

각 파트의 최종 목적은 개별 API 완성이 아니라 아래 핵심 사용자 흐름을 외부 배포 환경에서 끝까지 실행 가능하게 만드는 것이다.

```text
Guest Session
→ 사용자 설정
→ Routine 생성
→ DailyRoutine 확인
→ CHECK 또는 PHOTO 인증
→ 완료
→ Point Claim
→ Item / Story 성장
→ Avatar 변화 확인
```

이 흐름을 가장 먼저 안정적으로 완성하고, 이후 Speech / Record / Competition / Home의 완성도를 높인다.
