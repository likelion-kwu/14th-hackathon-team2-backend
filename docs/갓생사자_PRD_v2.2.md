> **v2.0 변경 요약** 루틴 카테고리를 `SKIN / WELL_BEING / HEALTH_FIT / DIET / TO_DO`로 확정하고, `TO_DO`는 특정 날짜의 1회성 루틴으로 처리한다. 카테고리별 추천 루틴은 실시간 AI 생성이 아니라 서버의 사전 검수 추천 Pool에서 기본 3개를 제공하고 사용자가 선택한 뒤 기존 루틴 생성 폼을 완성하는 방식으로 확정했다. PHOTO/CHECK 인증 완료 시 포인트를 자동 지급하지 않고, 사용자가 같은 `serviceDate` 안에서 완료된 루틴을 눌러 직접 수령한다. PHOTO는 10P, CHECK는 5P이며 하루 최대 3개 완료 루틴에서만 포인트를 받을 수 있다. 미수령 포인트는 자정 이후 소멸한다. 아이템은 누적 획득 포인트 100P마다 랜덤 1개를 영구 해금하며 포인트는 차감하지 않는다. 기존 누적 하루 성공일 기반 아이템 milestone은 폐기한다. 경쟁하기는 소비 기능 없이 해당 달에 수령한 포인트 합계로 전체 사용자의 순위를 계산하고 동점은 공동 순위로 처리한다. 연속 하루 성공 7/14/21/28/35회의 Story 해금 정책은 유지한다.

> **v1.8 변경 요약** MVP 루틴은 자정을 넘길 수 없도록 단순화했다. 시작 시간과 종료 시간은 같은 `serviceDate` 안에 있어야 하며 `startTime < endTime`을 필수 검증한다. `24:00` 입력은 지원하지 않고 하루 마지막 종료 시각은 `23:59`로 표현한다. 00:00 이후에는 전날 DailyRoutine을 홈/오늘 루틴에 노출하지 않는다.

> **v1.6 변경 요약** 루틴 인증 가능 시간을 서버에서 강제하고 종료 시간이 지난 미인증 루틴을 실패로 처리하도록 확정했다. 당시 자정 넘김 루틴도 허용했으나, **v1.8에서 MVP 단순화를 위해 자정 넘김 지원을 폐기했다.**  
> **v1.5 변경 요약** 문서 정합성을 보정하고, 당일 루틴 집합의 소급 변경으로 하루 성공·연속 기록이 왜곡되지 않도록 `serviceDate`별 루틴 집합 고정 규칙을 추가했다. 경험치/XP 제거, 누적 하루 성공일 기반 아이템 해금, 연속 하루 성공일 기반 스토리 해금, 스토리 연동 3단계 아바타 외형 정책은 유지한다.  
> **v1.4 변경 요약** 경험치 시스템을 제거하고, 랜덤 아이템 해금 기준을 누적 개별 루틴 완료 횟수에서 누적 하루 전체 루틴 성공 횟수로 변경했다. 연속 하루 성공 10/20회 스토리 해금은 유지하며, EP.1/EP.2 해금에 따라 아바타 외형이 2/3단계로 변화한다. 사진 인증과 체크 인증의 추가 차등 정책은 TBD로 변경했다.

### 핵심 제품 루프

```text
루틴 설정
→ 실제 행동 순간 사진/체크 인증
→ 사진 인증 시 AI 확인
→ 개별 루틴 완료 상태 반영
→ 완료된 루틴을 눌러 포인트 수령(PHOTO 10P / CHECK 5P, 하루 최대 3개)
→ 누적 획득 포인트 100P마다 랜덤 아이템 해금(포인트 차감 없음)

→ 연속 성공일 milestone에서 스토리 해금 및 아바타 외형 변화
→ 내 말투의 피드백
→ 다음 루틴 행동으로 연결
```

> **TO_DO 예외:** `TO_DO`는 특정 날짜에 수행하는 1회성 보조 작업이다. PHOTO/CHECK 인증과 완료 기록은 가능하지만 오늘 진행률의 분자·분모, DailySuccess, 누적/연속 성공일, Story, Point Claim, Item 해금, Competition Point 계산에는 포함하지 않는다.

# 1. 제품 개요

## 1.1 제품명

**갓생사자**  
현재 프로젝트에서 사용하는 가칭이며 추후 변경될 수 있다.

## 1.2 한 줄 설명

**미래의 나를 표현한 AI 아바타가 사용자의 말투로 루틴을 독려하고, 매일 다른 사진 미션을 통해 피부·생활 루틴을 인증하면 아바타가 성장하는 웰니스 루틴 서비스다.**

## 1.3 핵심 기획 문장

> 우리는 피부·생활 루틴을 꾸준히 유지하고 싶지만 변화가 바로 보이지 않아 쉽게 중단하는 20~30대 사용자가 겪는 지속성 문제를, 사진 인증과 개인화된 미래 아바타의 성장·피드백으로 해결하여 루틴을 계속 실행할 동기를 만든다.

---

# 2. 해결하려는 문제

피부 관리와 생활 습관은 하루나 이틀 실천한다고 결과가 바로 보이지 않는다. 세안, 보습, 선크림, 수분 섭취, 수면 준비 같은 행동은 반복이 중요하지만 현재 행동과 미래 결과 사이의 간격이 길다.

사용자는 다음 이유로 루틴을 중단하기 쉽다.

- 변화가 바로 보이지 않아 현재 행동의 의미를 체감하기 어렵다.
- 단순 체크는 실제 행동을 하지 않아도 완료할 수 있다.
- 같은 기록을 반복하는 과정이 지루하다.
- 자신이 루틴을 이어가려는 이유를 쉽게 잊는다.
- 일반적인 알림은 개인에게 친숙한 피드백으로 느껴지지 않는다.

이 제품은 사용자의 행동을 단순 체크 기록이 아니라 **미래 아바타의 성장**으로 표현하고, 아바타가 사용자의 말투로 반응하게 해 현재 행동과 미래의 나를 연결한다.

---

# 3. 주요 사용자와 사용 상황

## 3.1 핵심 타깃

**피부·생활 루틴을 꾸준히 실천하고 싶은 20~30대**

특히 다음 특성을 가진 사용자를 주요 대상으로 한다.

- 새로운 루틴을 시작하지만 며칠 후 중단하는 사용자
- 피부 관리나 생활 습관의 결과가 늦게 나타나면 동기를 잃는 사용자
- 체크리스트만으로는 행동 동기가 충분하지 않은 사용자
- 캐릭터 성장·수집·꾸미기 요소에 흥미가 있는 사용자
- 자신의 말투와 비슷한 개인화 피드백에 흥미를 느끼는 사용자

## 3.2 주요 루틴 범위

서비스의 중심은 피부 관리 루틴이지만 다음과 같은 간단한 생활 루틴도 허용한다.

- 세안, 보습, 선크림 사용
- 물 마시기
- 수면 준비
- 가벼운 운동
- 사용자가 직접 등록한 간단한 생활 습관

**일상 전체를 관리하는 종합 건강 플랫폼으로 범위를 확대하지 않는다.**

# 4. 현재 방식의 한계

기존 루틴 앱의 일반적인 흐름은 `루틴 등록 → 알림 → 체크 → 기록`이다.

| 한계 | 사용자 문제 |
|---|---|
| 체크만으로 완료 가능 | 실제 행동과 기록이 분리될 수 있다 |
| 즉각적인 결과 부족 | 오늘 행동한 이유를 체감하기 어렵다 |
| 반복 기록 | 기록 자체가 귀찮은 일이 된다 |
| 일반적인 알림 | 개인적 연결감이 약하다 |

# 5. 제품 목표와 비목표

## 5.1 Product Goal

**사용자가 최소 7일 동안 피부·생활 루틴을 지속하도록 동기를 제공한다.**

이를 위해 다음 경험을 제공한다.

1. 사용자가 직접 루틴과 인증 물건을 설정한다.
2. 실제 행동 순간에 사진 미션을 수행한다.
3. `SKIN / WELL_BEING / HEALTH_FIT / DIET` 루틴 완료는 오늘 진행률에 반영되고, 완료 루틴에서 Point를 직접 수령하면 누적 Point와 Item 해금에 연결된다. 하루 전체 루틴 성공은 이 네 카테고리만 기준으로 누적·연속 성공 기록과 Story 해금에 연결된다. `TO_DO`는 완료·인증 기록만 남기며 이 성장/보상 계산에서는 제외한다.
4. 미래 아바타가 사용자의 말투로 행동을 독려한다.
5. 기록 화면에서 누적 행동을 확인한다.

## 5.2 제품이 하지 않는 것

MVP는 다음을 목표로 하지 않는다.

- 피부 질환 진단 및 의료적 판단
- 피부 개선 효과 예측 또는 보장
- 특정 화장품 효과 평가
- 사용자의 실제 미래 외모 예측
- 모든 생활 습관을 관리하는 종합 건강 플랫폼
- 사진으로 실제 루틴 수행을 완벽하게 증명
- 자유로운 AI 아바타 챗봇
- 사용자별 AI 모델 파인튜닝

아바타의 외형 변화는 실제 피부 상태나 미래 외모의 변화를 의미하지 않는다. **스토리 Episode 해금 단계에 따라 변화하는 게임 요소**다.

# 6. 핵심 사용자 흐름

## 6.1 신규 일반 사용자

```text
서비스 진입
→ 게스트 시작
→ 닉네임 필수 입력
→ 아바타 설정
→ 말투 설정(카카오톡 또는 프리셋 중 1개 필수)
→ 메인 화면 진입
→ 카테고리 선택 및 직접 입력/추천 루틴 선택
→ 루틴 생성 및 인증 물건 선택
→ 오늘의 루틴 확인
→ 인증 시작
→ 사진 미션 확인
→ 사진 촬영 또는 체크 인증
→ 사진 인증 시 AI 판정
→ 개별 루틴 완료 상태 저장
→ `TO_DO`를 제외한 완료 루틴을 눌러 당일 Point 수령(PHOTO 10P / CHECK 5P, 하루 최대 3개)
→ 누적 획득 Point 100P milestone 확인 및 랜덤 아이템 해금
→ 오늘 적용된 `SKIN / WELL_BEING / HEALTH_FIT / DIET` 루틴 완료 여부 확인
→ 하루 성공 시 누적 성공일 +1 및 연속 성공일 +1
→ 연속 성공일 milestone 확인 및 Episode 해금
→ 해금된 Episode에 따른 아바타 외형 단계 반영
→ 기록 확인
```

## 6.2 사진 인증이 어려운 경우

```text
루틴 인증 시작
→ 사진 미션 확인
→ 촬영 불가 또는 인증 실패
→ 체크 인증 선택
→ 아바타 확인 대사
→ 체크 인증
→ 루틴 완료 상태 저장
```

사진 인증과 체크 인증은 모두 루틴 완료로 인정한다. 다만 `TO_DO`는 완료 기록만 남고 진행률·하루 성공·Story·Point에 반영하지 않는다. 인증 성공 자체에서는 Point를 지급하지 않으며, 같은 `serviceDate` 안에서 `TO_DO`를 제외한 완료 루틴을 눌러 Point를 수령할 때 PHOTO는 10P, CHECK는 5P를 지급한다. 하루 최대 3개 Point 대상 루틴에서만 수령할 수 있다.

# 8. 아바타

## 8.1 역할

아바타는 서비스의 중심 시각 요소다.

- 메인 화면의 중심 캐릭터
- 루틴 상황별 개인화 대사 제공
- 사진 인증 미션 안내
- Story 해금에 따른 3단계 외형 성장
- 사용자가 해금한 Item의 시각적 장착

## 8.2 성장 트랙

온보딩에서 사용자는 다음 네 개 중 **성장 트랙 1개를 선택**한다.

```text
SKIN
WELL_BEING
HEALTH_FIT
DIET
```

`TO_DO`는 Routine category이지만 Avatar 성장 트랙에는 포함하지 않는다.

- MVP에서는 최초 선택한 성장 트랙을 변경할 수 없다.
- 성장 트랙은 실제 건강 상태를 진단하거나 사용자의 미래 모습을 예측하기 위한 값이 아니다.
- 트랙별 Stage 변화는 미리 정한 시각적 게임 프리셋이다.

## 8.3 사용자 얼굴 사진

사용자 얼굴 사진 업로드는 **선택 사항**이다.

사진을 제공한 경우:

- 사용자와 닮은 느낌을 주기 위한 **얼굴 특징 참고용**으로만 사용한다.
- 얼굴형, 눈매, 헤어라인, 전반적인 인상처럼 캐릭터 얼굴을 개인화하는 데 필요한 범위만 참고한다.
- 안경·의상·액세서리 등 장착 Item을 사용자 사진에서 추출하지 않는다.
- 몸, 포즈, 체형, 전신 스타일을 사용자 사진에 맞춰 변경하지 않는다.
- 실제 피부 상태, 안색, 붓기, 건강 상태를 분석해 Stage를 결정하지 않는다.

사진을 제공하지 않은 경우에는 **디자이너가 준비한 기본 얼굴 템플릿**을 사용한다.

업로드 안내 기준:

- 한 명의 얼굴
- 정면 또는 정면에 가까운 사진
- 얼굴이 충분히 보이는 사진
- 마스크, 손 등으로 얼굴 대부분이 가려진 사진은 사용하지 않음

사용자 원본 얼굴 사진은 장기 저장하지 않는다. 각 생성 요청의 처리가 끝나면 성공/실패와 관계없이 서버 임시 파일을 삭제한다.

## 8.4 Stage 이미지 생성

최초 Avatar 설정에서 **Stage 1/2/3 이미지를 모두 미리 생성하고 저장**한다.

```text
고정 Avatar Template
+ 선택한 성장 트랙
+ (선택) 사용자 얼굴 Reference
        ↓
      Stage 1
       ↙   ↘
 Stage 2   Stage 3
```

생성 규칙:

1. 고정 템플릿의 몸, 포즈, 크기와 전체 캐릭터 스타일을 유지한 Stage 1을 생성한다.
2. Stage 2는 생성된 Stage 1을 기준 이미지로 사용한다.
3. Stage 3도 생성된 Stage 1을 기준 이미지로 사용한다.
4. Stage 2를 다시 Stage 3의 입력으로 이어 붙이지 않는다.
5. 세 Stage는 동일 인물·동일 포즈·동일 신체 위치를 유지해야 한다.
6. Stage 간 차이는 같은 캐릭터라는 느낌을 유지하면서 화면에서 식별 가능한 정도로 표현한다.

## 8.5 성장 트랙별 3단계 표현

트랙별 변화는 사용자 사진의 실제 상태를 분석한 결과가 아니라 **고정된 시각 프리셋**이다.

### SKIN

```text
Stage 1 → 피부가 상대적으로 덜 정돈된 캐릭터 표현
Stage 2 → 중간 단계
Stage 3 → 더 깨끗하고 균일하게 정돈된 캐릭터 표현
```

실제 피부 질환이나 트러블 정도를 판정하지 않는다.

### WELL_BEING

```text
Stage 1 → 다소 피곤하고 칙칙한 안색의 캐릭터 표현
Stage 2 → 중간 단계
Stage 3 → 더 밝고 생기 있는 안색의 캐릭터 표현
```

### HEALTH_FIT / DIET

```text
Stage 1 → 얼굴이 조금 부어 보이는 캐릭터 표현
Stage 2 → 중간 단계
Stage 3 → 얼굴 붓기가 더 빠져 보이는 캐릭터 표현
```

`HEALTH_FIT`과 `DIET`는 별도 성장 트랙이지만 MVP Avatar의 Stage 변화 프리셋은 동일한 얼굴 붓기 변화 계열을 사용할 수 있다.

**모든 트랙에서 체형 변화는 사용하지 않는다.**

## 8.6 이미지 규격과 저장

최종 Avatar Stage asset 규격은 다음으로 고정한다.

```text
250 × 500 px
PNG
RGBA 투명 배경
동일 캔버스
동일 포즈
동일 신체 위치
```

AI가 더 큰 해상도로 결과를 반환하더라도 최종 저장 전 고정 템플릿 좌표를 기준으로 250×500 RGBA PNG로 정규화한다.

생성된 Stage 1/2/3 이미지는 **백엔드가 사용하는 가비아 서버 host disk**에 장기 저장한다. Docker 배포 시 컨테이너 내부 임시 파일시스템이 아니라 host directory를 volume/bind mount하여 사용한다.

DB에는 이미지 binary를 넣지 않고 현재 활성 Avatar asset set의 논리 key만 저장한다.

## 8.7 재생성 및 실패 처리

온보딩에서 사용자는 Avatar **재생성을 1회** 수행할 수 있다.

재생성은 Stage 하나만 바꾸지 않고 Stage 1/2/3을 새 세트로 다시 만든다.

```text
기존 세트 A 유지
→ 새 세트 B 생성
→ B의 Stage 1/2/3 모두 성공
→ DB의 활성 asset set을 B로 교체
→ 교체 완료 후 A 파일 삭제
```

새 세트 생성에 실패하면 기존 세트를 삭제하거나 일부 파일만 교체하지 않는다.

사용자 얼굴 사진은 서버에 보관하지 않으므로 재생성에서 같은 얼굴을 사용하려면 프론트가 온보딩 중 보유한 원본 File을 다시 전송하거나 사용자가 다시 선택해야 한다. 서버는 재생성 요청에서도 사진을 처리 후 즉시 삭제한다.

초기 생성 실패 처리:

```text
AI 생성 실패
→ 자동 1회 재시도
→ 다시 실패
→ 트랙별 기본 Stage 1/2/3 세트 사용
→ 온보딩 계속 진행
```

따라서 외부 AI 이미지 생성 장애가 Home 진입을 막지 않아야 한다.

## 8.8 Story 연동 외형 단계와 노출

MVP Story Episode는 5개지만 Avatar 외형은 총 3단계다.

```text
Story 미해금 → Stage 1
EP.1 해금     → Stage 2
EP.2 해금     → Stage 3
EP.3 해금     → Stage 3 유지
EP.4 해금     → Stage 3 유지
EP.5 해금     → Stage 3 유지
```

- 현재 Stage는 저장된 성장값이나 XP가 아니라 영구 해금된 Story Episode에서 파생한다.
- 연속 기록이 끊겨도 이미 해금된 Story와 Avatar Stage는 퇴화하지 않는다.
- Stage 2/3 이미지는 초기 설정 때 미리 생성해도 실제 Story 해금 전에는 사용자에게 노출하지 않는다.
- 프론트에는 **현재 Stage 이미지**를 기본 제공한다.

## 8.9 Item 장착 표현

Item 이미지는 프론트 정적 asset으로 관리한다.

```text
Avatar Stage PNG 250×500
+ Item PNG 250×500
+ Item PNG 250×500
→ 프론트 overlay
```

- 모든 장착 Item PNG는 Avatar와 같은 250×500 투명 캔버스를 사용한다.
- Item 여러 개를 동시에 장착할 수 있다.
- MVP에서는 backend가 Item의 x/y 좌표, body part, layer 좌표를 저장하지 않는다.
- 장착 상태의 Source of Truth는 backend의 `UserItem.equipped`다.
- 프론트는 `assetKey`를 정적 Item PNG와 매핑하고 정해진 렌더 순서로 겹쳐 표시한다.
- AI 이미지 API를 Item 장착/해제 때마다 다시 호출하지 않는다.

# 9. 말투 설정

사용자는 최초 설정에서 다음 두 방식 중 **하나를 반드시 선택**한다.

1. 카카오톡 대화 ZIP 기반 말투 분석
2. 준비된 프리셋 기반 말투 설정

두 방식은 동시에 활성화하지 않는다.

세부 구현은 `speech_style_system_SRS_v2.5.md`를 최우선 기준으로 사용한다.

## 핵심 제품 요구사항

- 사용자의 메시지만 말투 분석 대상으로 사용
- 상대방 메시지는 문맥 이해에만 사용
- 유효 메시지 50개 이상일 때 분석
- 최신 최대 500개 사용
- 분석 후 카카오톡 원본 및 임시 데이터 삭제
- 장기 저장 대상은 말투 프로필 JSON, 사용자 수정값, 대표 예시 최대 20개, 사전 생성 대사 40개 및 필요한 메타데이터로 제한
- 아바타 대사 최대 50자
- 욕설 기본 OFF
- 실제 사용자 대화에서 탐지된 욕설만 선택적으로 허용
- 인신공격·혐오·협박·자해 유도 등 금지
- 말투 세부 설정 수정은 MVP Must이며, 수정 시 기존 사전 생성 대사 40개를 새 설정으로 전부 재생성
- 8개 상황마다 5개씩 총 40개의 사전 생성 대사를 생성·저장
- 사용자는 현재 말투를 초기화할 수 있으며, 초기화 후 새 말투를 설정하기 전까지 홈으로 진입할 수 없음

### 말투 초기화 정책

사용자가 `말투 초기화`를 실행하면 현재 말투 방식이 카카오톡 기반인지 프리셋 기반인지와 관계없이 다음 말투 관련 데이터를 모두 삭제한다.

- 활성 말투 방식 및 프리셋 선택값
- 말투 프로필 JSON
- 사용자 수정값
- 대표 예시
- 사전 생성 대사 40개 및 대사 사용 이력
- 욕설 탐지·사용 설정 등 말투 관련 설정
- 말투 분석 메타데이터

닉네임, 아바타, 루틴, 누적 하루 성공 기록, 연속 하루 성공 기록, 획득 아이템, 스토리 해금, 인증 기록 등 말투와 무관한 사용자 데이터는 유지한다.

초기화 완료 후 사용자는 말투 설정 화면으로 이동하며, 카카오톡 또는 프리셋 중 하나를 다시 설정해야 홈을 사용할 수 있다.

# 10. 루틴

## 10.1 루틴 카테고리

MVP 루틴 카테고리는 다음 5개로 고정한다.

```text
SKIN
WELL_BEING
HEALTH_FIT
DIET
TO_DO
```

- `SKIN`: 피부 관리 행동
- `WELL_BEING`: 수분, 수면 준비 등 일상 웰빙 행동
- `HEALTH_FIT`: 운동·활동 루틴
- `DIET`: 식사 관련 간단한 행동
- `TO_DO`: 특정 날짜에 한 번 수행하는 일회성 할 일

복잡한 하위 카테고리나 의료/질환 분류는 만들지 않는다.

### TO_DO 진행·보상 정책

`TO_DO`는 사용자가 당일 할 일을 기록하고 완료하기 위한 **보조 작업**이다.

- `DailyRoutine`으로 생성하고 PHOTO/CHECK 인증할 수 있다.
- 완료된 `TO_DO`에는 `RoutineVerification`을 저장한다.
- 오늘 진행률의 완료 수와 전체 수에 포함하지 않는다.
- `DailySuccessRecord` 생성 조건에 포함하지 않는다.
- 누적/연속 하루 성공 및 Story streak에 영향을 주지 않는다.
- `RoutinePointClaim` 대상이 아니므로 PHOTO/CHECK 방식과 관계없이 Point를 지급하지 않는다.
- 따라서 Item 해금과 Competition Point에도 기여하지 않는다.
- 이 제외 정책을 위해 별도 status/counter를 저장하지 않고 `DailyRoutine.category_snapshot == TO_DO` 여부로 계산에서 제외한다.

## 10.2 카테고리별 추천 루틴

루틴 추가 화면에서 사용자는 직접 내용을 입력하거나 선택한 카테고리의 추천 루틴을 사용할 수 있다.

MVP 추천 방식은 **서버의 사전 검수 Recommendation Pool**이다. 실시간 OpenAI 생성은 사용하지 않는다.

```text
카테고리 선택
→ 서버가 해당 카테고리 추천 후보 중 기본 3개 반환
→ 이미 등록된 동일/유사한 추천은 가능한 범위에서 제외
→ 사용자가 추천 1개 선택
→ 기존 루틴 생성 폼의 내용과 권장 인증 물건을 채움
→ 사용자가 날짜/요일·시간·인증 물건을 최종 확인
→ 저장
```

추천은 사용자의 승인 없이 루틴을 자동 저장하거나 수정하지 않는다. 추천 데이터는 MVP에서는 코드/JSON/YAML 설정으로 관리하며 별도 추천 테이블이나 AI 추천 모델을 만들지 않는다.

## 10.3 루틴 생성 입력값

반복 루틴(`SKIN / WELL_BEING / HEALTH_FIT / DIET`)은 다음 값을 받는다.

- 카테고리
- 루틴 내용
- 시작 시간
- 종료 시간
- 반복 설정: 매일 또는 특정 요일 복수 선택
- 인증 물건

`TO_DO`는 다음 값을 받는다.

- 카테고리 = `TO_DO`
- 할 일 내용
- 수행 날짜
- 시작 시간
- 종료 시간
- 인증 물건

## 10.4 반복 설정

반복 타입은 다음 세 가지다.

```text
DAILY
DAYS_OF_WEEK
ONCE
```

- `SKIN / WELL_BEING / HEALTH_FIT / DIET`: `DAILY` 또는 `DAYS_OF_WEEK`
- `TO_DO`: `ONCE`만 허용
- `ONCE`는 사용자가 선택한 특정 날짜에 DailyRoutine을 정확히 한 번 생성한다.

## 10.5 루틴 시간 범위

MVP에서는 **자정을 넘는 루틴을 지원하지 않는다.**

모든 루틴은 하나의 `serviceDate` 안에서 시작하고 종료해야 한다.

```text
startTime < endTime
```

을 필수 조건으로 한다.

예:

```text
07:00~09:00  허용
22:00~23:59  허용
23:00~01:00  허용하지 않음
20:00~08:00  허용하지 않음
09:00~09:00  허용하지 않음
```

`24:00`은 API/DB 시간 값으로 지원하지 않는다. 하루 마지막 종료 시각이 필요한 경우 `23:59`를 사용한다.

시간 입력 정밀도는 분 단위(`HH:mm`)로 통일한다. 종료 시각으로 선택한 분 전체를 인증 가능 구간에 포함하며, 다음 분부터 종료된 것으로 본다.

## 10.6 루틴 인증 가능 시간

루틴은 **설정된 수행 시간 안에서만** 사진 또는 체크 인증할 수 있다.

서버는 클라이언트 시간이 아니라 서버 기준 시간으로 인증 가능 여부를 판정한다.

```text
현재 시각 < 실제 시작 시각
→ 인증 불가: 아직 시작 전

실제 시작 시각 <= 현재 시각 <= 실제 종료 시각
→ 인증 가능

현재 시각 > 실제 종료 시각
→ 인증 불가: 실패 확정
```

종료 시간이 지난 뒤에는 사진과 체크 인증 모두 허용하지 않는다. PHOTO 요청이 종료 전 서버에 도착했다면 최초 서버 수신 시각을 기준으로 유효성을 판정한다.

## 10.7 당일 적용 및 `serviceDate`별 루틴 집합 고정

오늘 현재 시간보다 이른 시간대의 루틴을 새로 추가하거나, 이미 시작 시간이 지난 루틴을 수정·삭제하여 오늘의 수행 대상을 소급 변경하지 않는다. 이런 변경은 **다음 적용 가능한 반복일부터 반영**한다.

같은 `serviceDate`에서 성공한 루틴 인증이 1건이라도 생성된 이후에는 그 `serviceDate`의 DailyRoutine 집합을 고정한다. 첫 성공 인증 이후의 생성·수정·삭제는 해당 날짜의 진행률 분모와 하루 성공 판정을 바꾸지 않는다.

`TO_DO`도 생성된 해당 날짜의 DailyRoutine이 동일한 집합 고정 규칙을 따른다.

## 10.8 수정·삭제

- 수정은 기존 값이 채워진 생성 폼과 동일한 양식에서 수행한다.
- 삭제는 루틴 팝업의 개별 루틴에서 수행한다.
- 이미 확정된 인증·포인트 수령·하루 성공·아이템·Story 해금 기록은 수정·삭제로 취소하지 않는다.
- 별도의 루틴 관리 페이지는 만들지 않는다.

# 11. 인증 물건과 사진 미션

## 11.1 인증 물건

인증 물건은 **루틴 생성 시 사용자가 직접 선택**한다.

MVP에서는 시스템이 지원하는 공통 물건 목록 중 하나를 선택하게 한다.

예시:

- 컵
- 물병
- 화장품 용기
- 수건
- 칫솔
- 기타 AI 판정 테스트가 완료된 지원 항목

사용자가 자유 텍스트로 인증 물건을 작성하도록 하지 않는다.

## 11.2 사진 미션

사진 인증 시 다음 두 요소를 결합한다.

```text
루틴 생성 시 선택한 인증 물건
+
오늘의 손동작 미션
```

예:

```text
인증 물건: 컵
손동작 미션: 엄지척
→ "컵을 들고 엄지척 해주세요."
```

손동작 미션은 사전 정의된 풀에서 선택하고, 같은 미션이 연속 반복되지 않도록 한다.

AI를 이용한 미션 자동 생성은 Must가 아니다.

# 12. 사진 인증

## 12.1 기본 방식

사진 인증을 기본 인증 방식으로 제공한다. 가능하면 서비스 내부 카메라로 즉시 촬영한다.

## 12.2 AI 판정 대상

AI는 다음만 확인한다.

1. 루틴 생성 시 선택한 인증 물건이 사진에 있는가
2. 오늘의 손동작 미션을 수행했는가
3. 사진이 판정 가능한 품질인가

AI는 사용자가 루틴 행동 자체를 실제로 수행했는지 완벽하게 증명하지 않는다.

예: `물 마시기` 루틴에서 AI는 **컵 + 엄지척**을 확인하지만 실제로 물을 마셨는지는 판정하지 않는다.

## 12.3 성공·실패 처리

- 인증 요청 시각이 루틴 수행 시간 안에 있고 필수 조건을 충족하면 사진 인증 성공
- AI 판정이 불확실하거나 실패하면, **아직 루틴 종료 시각 전인 경우에만** `다시 촬영` 또는 `체크 인증으로 전환`
- 루틴 종료 시각이 지난 뒤에는 새 사진 인증·재촬영·체크 전환을 허용하지 않음
- 종료 후 새 사진 요청은 AI 판정을 시작하지 않고 실패 응답

## 12.4 사진 저장 정책

사진 원본은 AI 판정에만 일시적으로 사용하고 **판정 완료 후 삭제**한다.

- 장기 보관하지 않음
- 기록 화면에서 원본 사진을 다시 보여주지 않음
- 인증 사진 갤러리를 만들지 않음

# 13. 체크 인증

사진을 찍기 어려운 사용자는 체크 인증으로 전환할 수 있다.

- 체크 인증도 해당 루틴의 설정된 수행 시간 안에서만 가능하다.
- 종료 시간이 지난 미인증 루틴에는 체크 인증을 허용하지 않는다.
- 아바타가 사용자 말투로 짧은 확인 대사를 제공한다.
- 사용자가 수행 시간 안에 확인하면 해당 루틴을 완료 처리한다.
- 인증 성공 자체에서는 포인트를 자동 지급하지 않는다.
- `TO_DO`를 제외하고 같은 `serviceDate`에 완료된 루틴을 사용자가 직접 눌러 Point를 수령한다.
- Point 대상 PHOTO 완료 루틴은 10P, CHECK 완료 루틴은 5P다.
- `TO_DO`는 PHOTO/CHECK 인증 방식과 관계없이 Point Claim 비대상이다.
- 한 `serviceDate`에서 최대 3개 Point 대상 완료 루틴만 Point를 수령할 수 있다.
- Point를 수령하지 않고 날짜가 바뀌면 해당 완료 루틴의 미수령 Point는 소멸한다.

예시 대사:

- "진짜 한 거 맞지?"
- "오늘은 믿는다."

# 14. 아이템·스토리·아바타 외형

## 14.1 인증과 포인트 수령

사진 인증과 체크 인증은 모두 **개별 루틴 완료**로 인정한다. 다만 오늘 진행률과 하루 전체 성공 판정에는 `SKIN / WELL_BEING / HEALTH_FIT / DIET`만 반영하고 `TO_DO`는 제외한다.

Point는 인증 성공 시 자동 지급하지 않는다. 사용자가 루틴 목록에서 `COMPLETED` 상태인 **Point 대상 루틴(`TO_DO` 제외)**을 눌러 별도로 수령한다.

```text
PHOTO 완료 루틴 → 10P
CHECK 완료 루틴 → 5P
```

포인트 수령 규칙:

1. 해당 DailyRoutine에 성공 `RoutineVerification`이 있어야 한다.
2. 해당 DailyRoutine의 `category_snapshot`이 `TO_DO`가 아니어야 한다. `TO_DO`는 인증 방식과 관계없이 Point 수령 대상이 아니다.
3. 포인트는 해당 `serviceDate` 당일에만 수령할 수 있다.
4. 동일 `serviceDate`에서 사용자당 최대 3개 완료 루틴까지만 수령할 수 있다.
5. 동일 DailyRoutine에서 포인트를 중복 수령할 수 없다.
6. 하루 3개를 이미 수령한 뒤 다른 완료 루틴을 눌러도 루틴 완료 상태는 유지되지만 추가 포인트는 지급하지 않는다.
7. 날짜가 바뀌면 전날의 미수령 포인트는 소멸한다.

포인트는 MVP에서 소비하지 않는다. 따라서 `현재 잔액`이나 차감 거래 개념을 만들지 않고 **누적 획득 점수**로 취급한다.

## 14.2 누적 포인트 기반 랜덤 아이템 해금

사용자가 실제로 수령한 포인트의 **누적 획득 합계가 100P 단위 milestone을 새로 넘을 때마다** 미보유 활성 아이템 중 하나를 무작위로 영구 해금한다.

```text
100P → Item 1개
200P → Item 1개
300P → Item 1개
...
```

- Item 해금으로 포인트를 차감하지 않는다.
- 이미 처리한 100P milestone은 다시 처리하지 않는다.
- 이미 보유한 Item은 후보에서 제외한다.
- 미보유 활성 Item이 없으면 중복 지급하지 않고 해당 milestone을 처리 완료로 기록한다.
- 기존 `누적 하루 성공일 1/3/5/10/20/30/40/50 → Item` 정책은 폐기한다.

### Item 장착 asset 규칙

- Item 실제 PNG는 프론트 정적 asset으로 관리한다.
- 모든 Item PNG는 Avatar와 같은 250×500 투명 캔버스를 사용한다.
- 사용자는 보유 Item 여러 개를 동시에 장착할 수 있다.
- Backend는 장착 Item ID와 `assetKey`만 관리하며 좌표/파츠/레이어 데이터를 저장하지 않는다.
- 프론트는 현재 Stage Avatar PNG 위에 장착 Item PNG를 overlay한다.

## 14.3 하루 전체 루틴 성공

하루 성공은 다음과 같이 정의한다.

> 해당 `serviceDate`에 `SKIN / WELL_BEING / HEALTH_FIT / DIET` DailyRoutine이 1개 이상 존재하고, 그 날짜의 **해당 네 카테고리 루틴을 모두 완료**하면 하루 성공으로 계산한다. `TO_DO`는 존재·성공·실패 여부와 관계없이 이 판정에서 제외한다.

- 하루 성공과 Point 수령은 독립적이다. 그날 Point를 0개만 수령해도 Point 대상 네 카테고리 루틴을 모두 인증했다면 하루 성공이다.
- Point 대상 네 카테고리 루틴이 있는 날 해당 루틴 모두 완료: 누적 성공일 +1, 연속 성공일 +1
- Point 대상 네 카테고리 루틴 중 하나 이상 종료 시각까지 미인증: 누적 성공일 변화 없음, 연속 성공 기록 중단
- Point 대상 네 카테고리 루틴이 없고 `TO_DO`만 있는 날도 성공일로 세지 않으며 연속 기록을 끊지 않는다
- 적용 루틴 자체가 없는 날: 누적/연속 증가 없음, 연속 기록 중단 없음
- 동일 `serviceDate`는 하루 성공으로 중복 집계하지 않는다.

누적 하루 성공일은 기록·분석 지표로 유지하지만 Item 해금 조건으로 사용하지 않는다. 연속 성공일은 Story 해금 조건으로 사용한다.

## 14.4 Story Episode 해금

Story는 **연속 하루 전체 루틴 성공 횟수**를 기준으로 해금한다.

| Episode | 해금 조건 |
|---|---|
| EP.1 | 하루 전체 루틴 성공 7회 연속 |
| EP.2 | 하루 전체 루틴 성공 14회 연속 |
| EP.3 | 하루 전체 루틴 성공 21회 연속 |
| EP.4 | 하루 전체 루틴 성공 28회 연속 |
| EP.5 | 하루 전체 루틴 성공 35회 연속 |

Episode는 한 번 해금되면 다시 잠기지 않는다. 실제 Story 콘텐츠는 프론트 정적 asset으로 관리하며 백엔드는 해금 상태와 진행 조건만 관리한다.

## 14.5 Story 단계에 따른 아바타 외형 변화

```text
Story 미해금 → Stage 1
EP.1 해금     → Stage 2
EP.2 해금     → Stage 3
EP.3~EP.5     → Stage 3 유지
```

연속 기록이 끊겨도 이미 해금한 Episode와 Avatar Stage는 퇴화하지 않는다.

## 14.6 경쟁하기 월간 랭킹

`경쟁하기`는 Point 소비 기능이 아니라 **한 달 동안 누가 더 많은 Point를 수령했는지 보여주는 월간 랭킹**이다.

- 기준: `Asia/Seoul` 달력 월의 Point 수령 합계
- 해당 달에 실제로 수령한 PHOTO/CHECK Point만 합산하며, `TO_DO`는 Point Claim 자체가 불가능하므로 랭킹에 포함되지 않음
- 다음 달이 시작되면 월간 랭킹 점수는 새 달 데이터로 다시 계산
- 과거 누적 Point와 Item 해금 기록은 유지
- 동점 사용자는 공동 순위
- 공동 순위 뒤의 다음 순위는 일반 경쟁 순위 방식으로 계산한다. 예: `1, 2, 2, 4`
- MVP에서는 Point 사용/차감, 배팅, 참가비, 부스트, Battle Pass를 만들지 않는다.

## 16.1 월간 기록 캘린더(Must)

월간 캘린더는 별도 저장 상태를 만들지 않고 `GET /api/v1/records`의 날짜별 기록을 사용한다. 캘린더의 진행률 대상은 `SKIN / WELL_BEING / HEALTH_FIT / DIET`이며 `TO_DO`는 제외한다. `TO_DO`만 존재하는 날짜는 진행률 대상 루틴이 없는 날짜와 동일하게 표시한다.

표시 규칙은 다음과 같다.

| 상태 | 서버 기록 기준 | 표시 |
|---|---|---|
| 진행률 대상 루틴 없음 | `totalCount == 0` | 표시 없음 |
| 아무 루틴도 완료하지 못한 과거 날짜 | `totalCount > 0 && completedCount == 0` | 빨강 X |
| 일부 완료 | `0 < completedCount < totalCount` | 노랑 - |
| 모두 완료 | `totalCount > 0 && completedCount == totalCount` | 초록 ✓ |
| 미래 날짜 | 아직 수행 대상 결과가 확정되지 않음 | 표시 없음 |

오늘 날짜는 예외적으로 `completedCount == 0`이라고 즉시 빨강 X로 표시하지 않는다. 오늘 `dayStatus`가 아직 `NO_ROUTINE` 또는 `IN_PROGRESS`라면 중립/빈칸으로 두고, 진행률 대상 루틴의 실패가 확정되어 `dayStatus == FAILED`가 된 경우에만 빨강 X를 표시한다. 오늘 일부라도 완료했다면 `dayStatus`와 관계없이 일부 완료는 노랑 -, 전부 완료는 초록 ✓로 표시한다.

캘린더 상단의 **“이번 달 N일 달성”**에서 `N`은 표시 월의 초록 ✓ 날짜 수다. 이는 해당 월의 `DailySuccessRecord` 수와 동일한 의미다.

사용자는 이전 달과 다음 달을 자유롭게 이동할 수 있다. 미래 월/미래 날짜를 열 수는 있지만 미래 날짜에는 완료 상태 아이콘을 표시하지 않는다.

월간 캘린더 때문에 별도 Calendar API, Calendar 테이블, 월별 상태 컬럼 또는 통계 스냅샷을 추가하지 않는다. 한 달 조회는 기존 `GET /records?fromDate=YYYY-MM-01&toDate=YYYY-MM-DD`의 최대 31일 범위 안에서 처리한다.

# 22. 개인정보·건강 안전

## 22.1 카카오톡 데이터

- 원본 ZIP 장기 저장 금지

- 장기 저장은 말투 프로필 JSON, 사용자 수정값, 대표 예시 최대 20개, 사전 생성 대사 40개와 필요한 말투 메타데이터로 최소화

## 22.2 인증 사진

- 인증 판정용으로만 일시 사용
- 판정 완료 후 원본 삭제
- 장기 저장 및 갤러리 기능 없음

## 22.3 건강 표현

- 질병을 진단한다고 표현하지 않는다.
- 피부 또는 건강 개선을 보장하지 않는다.
- 아바타 성장을 실제 건강·피부 변화와 동일시하지 않는다.

## 22.4 아바타 생성용 얼굴 사진과 생성 이미지

- 얼굴 사진 업로드는 선택 사항이다.
- 얼굴 사진은 Avatar 얼굴 특징 참고용으로만 사용하며 실제 피부·안색·붓기 상태를 분석하지 않는다.
- 원본 얼굴 사진은 각 Avatar 생성/재생성 요청 종료 시 즉시 삭제한다.
- 생성된 Stage 1/2/3 PNG는 서비스 제공에 필요한 Avatar asset이므로 서버 host disk에 저장한다.
- 재생성을 위해 서버가 기존 원본 얼굴 사진을 보관하지 않는다.

# 25. MVP 완료 조건

1. 외부에서 접속 가능한 URL이 존재한다.
2. 일반 게스트로 서비스를 시작할 수 있다.
3. 별도 데모 모드 없이 발표용으로 미리 상태를 준비한 일반 게스트를 사용할 수 있다.
4. 닉네임을 입력하고 Avatar 성장 트랙 1개를 선택할 수 있다.
5. 선택적으로 얼굴 사진을 업로드하거나 기본 얼굴 템플릿으로 Avatar를 만들 수 있다.
6. 최초 Avatar 설정에서 Stage 1/2/3 세트가 준비되고 현재 Stage 이미지를 조회할 수 있다.
7. 원본 얼굴 사진이 각 생성 요청 종료 후 삭제된다.
8. Avatar 재생성을 온보딩에서 1회 수행할 수 있고 새 세트 성공 전 기존 세트가 유지된다.
9. 초기 AI Avatar 생성이 재시도 후 실패해도 기본 Stage 세트로 온보딩을 계속할 수 있다.
10. 말투 세부 설정 수정 및 상황별 사전 대사 40개 생성이 동작한다.
11. 말투 초기화 후 비말투 데이터는 유지되고 재설정 전 홈 진입이 차단된다.
12. `SKIN / WELL_BEING / HEALTH_FIT / DIET / TO_DO` 카테고리를 선택할 수 있다.
13. 반복 카테고리는 `DAILY / DAYS_OF_WEEK`, `TO_DO`는 특정 날짜 `ONCE`로 생성할 수 있다.
14. 카테고리별 사전 추천 루틴을 조회하고 선택해 생성 폼을 채울 수 있다.
15. 루틴을 생성·수정·삭제할 수 있고 당일 집합 고정 규칙이 적용된다.
16. `startTime < endTime`, 자정 넘김·`24:00` 금지 규칙이 적용된다.
17. 루틴 생성 시 지원 목록에서 인증 물건을 선택할 수 있다.
18. 오늘 루틴을 시간순으로 조회할 수 있다.
19. 사진 미션을 제공하고 PHOTO/CHECK 인증을 수행할 수 있다.
20. AI가 사진에서 인증 물건과 손동작을 판정한다.
21. 인증 실패 시 시간창 안에서 재촬영 또는 CHECK 전환이 가능하다.
22. 루틴 종료 이후 새 PHOTO/CHECK 인증이 거부된다.
23. 인증 완료 정보가 저장되며, `SKIN / WELL_BEING / HEALTH_FIT / DIET`만 오늘 진행률에 반영되고 `TO_DO`는 제외된다.
24. `TO_DO`를 제외한 완료 PHOTO/CHECK 루틴에서 각각 10P/5P를 같은 serviceDate 안에서 직접 수령할 수 있다.
25. `TO_DO` Point Claim이 차단되고, 동일 DailyRoutine Point 중복 수령과 serviceDate당 3개 초과 수령도 차단된다.
26. 미수령 Point는 serviceDate가 끝난 뒤 수령할 수 없다.
27. 누적 획득 Point 100P 단위마다 Point 차감 없이 미보유 Item 1개를 랜덤 해금할 수 있다.
28. 월간 획득 Point 기준 경쟁 Ranking을 조회할 수 있고 동점은 공동 순위로 처리되며 `TO_DO`는 랭킹 Point에 기여하지 않는다.
29. `TO_DO`를 제외한 하루 전체 루틴 성공 여부와 누적 성공일을 중복 없이 기록할 수 있다.
30. `TO_DO`를 제외한 연속 하루 전체 성공 기록을 계산할 수 있다.
31. 연속 7/14/21/28/35회에서 EP.1~EP.5가 각각 영구 해금된다.
32. EP.1에서 Stage 2, EP.2에서 Stage 3이 되고 EP.3~EP.5에서도 Stage 3을 유지한다.
33. 수행 기록, Point, 경쟁 순위, Item, Story 상태를 다시 조회할 수 있다.
34. 외부 AI 오류 상황을 처리할 수 있다.
35. 카카오톡 원본과 인증 사진이 정책대로 삭제된다.
36. 비밀키가 Git 저장소에 포함되지 않는다.
37. 다른 컴퓨터 또는 모바일 환경에서 접속 테스트를 완료한다.
38. 치명적인 오류 없이 핵심 사용자 흐름을 처음부터 끝까지 시연할 수 있다.
